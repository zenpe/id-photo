# 自有小程序上线与部署规划

## 目标与约定

目标设备为 fnOS / Intel N100，先交付可正式使用的免费图片工具，再按实际资格启用广告、会员和异步回调。
免费保存不限定在内测。当前阶段保留 Vue 2 / uni-app 2，使用 Node 24 与 Yarn 1.22.22。
架构迁移另开迭代，避免与发布修复同时进行。

本文件是实施计划；以下能力除“当前基线”列明的项目外，均不代表已经实现。

## 当前基线

- 单 API Compose 已提供，默认关闭支付；NAS 实际宿主机端口使用 8090。
- Node 24 依赖安装、小程序和 H5 构建、现有流程回归已在本机验证；新增 CI 配置尚待远端运行。
- MTCNN 空候选框修复已提交为 `0dc9fd4`，本机 7 项隔离回归通过；需要确认 Fork 与 NAS 是否已更新并完成真实照片验收。
- 标准版 Hivision MODNet 已改为前后端默认，属于当前未提交的修改；不等于 NAS 镜像已经更新。
- 上传错误的控制台诊断已补充，仍需通过真实请求定位持续的 Invalid HTTP request 警告。
- 免费保存开关尚未实现，客户端仍依赖现有广告授权流程。
- 当前 `src/manifest.json` 存在用户自行修改的 AppID，整理提交时须保留并单独确认是否作为仓库示例公开。

## 第 0 阶段：收拢当前修复，建立可回退基线

### 范围

1. 审查并分组提交 Node 24 适配、上传诊断、默认模型调整，避免混入本地密钥和无关个人配置。
2. 同步服务状态检查：证件照、人像抠图的默认模型应检查 Hivision MODNet，不再分别检查旧的 BiRefNet / 摄影人像模型。
3. 确认 MTCNN 修复到达 NAS。检测不到人脸时先重试原图，再返回明确业务错误；未知异常保留排查线索。
4. 保留当前可工作的 NAS 端口、Lucky 和 EdgeOne 配置，记录协议、端口、回源 Host 与超时。
5. 发布一个已验证的基线镜像标签，记录代码提交与本地配置备份位置。

### 验收

- 单人正脸成功生成；无人脸、多人脸返回清楚提示；失败后可继续选图。
- NAS 默认使用标准版，同时仍可选择其他已安装模型。
- `/health`、`/service-status` 与实际能力一致。
- 公网请求及局域网直连分别验证；HTTP 解析警告的来源另行定位，不通过关闭日志掩盖。
- 能回退镜像，数据目录和身份密钥不随重建丢失。

## 第 1 阶段：免费保存、自有配置和失败恢复

这是初版正式发布的主要交付范围，分三个小批次实现和验证。

### 1A. 保存与广告解耦

- 文件保存器只负责生成本地文件、相册权限、相册保存和电子照记录，不直接调用广告 SDK。
- 保存策略统一管理免费、会员和广告授权，所有结果页共用；覆盖证件照、抠图、水印、转换、电子照再次下载。
- 默认免费保存，购买关闭。候选运营配置包括保存模式、广告位、广告不可用处理策略、会员购买是否开放。
- 推荐广告无填充或加载失败时免费放行；用户主动中途关闭广告仍按明确告知的观看规则处理，二者分开。
- 会员资格继续由后端确认。查询异常时不把付费用户静默当普通用户强制看广告，应提供重试或按已明确的免费策略处理。
- 已完成广告后，相册授权失败、保存失败重试不重复看广告。一次制作任务的授权可供该任务的多次保存使用，任务或照片变更时重新计算。
- 普通按钮显示“保存照片”；确实需要广告时提前显示“看视频免费保存”，不等到最后才告知。

验收：没有广告位仍能完成全部免费保存；拒绝相册权限后能恢复；重复点击不并行保存；广告完成后的保存重试不再次观看；会员失败处理不误导。

### 1B. 自有配置与能力开关

- 前端公开配置：AppID、各环境 API 地址、品牌名称、客服入口及协议信息。
- 后端私密配置：微信 AppSecret、签名密钥、推送及支付密钥，保存在 NAS 本地，不进入镜像和 Git。
- 删除上游真实服务域名、广告位和客服的静默回退；示例使用明显占位值。
- 增加构建前检查：缺少正式 API、AppID、启用广告但未配置广告位等情况给出可操作错误。
- CI 使用明确的假配置验证构建，不需要真实生产凭据。
- 提供公开的能力/运营配置接口，返回广告、购买、异步检测等已配置且启用的能力及配置版本；不返回任何密钥。
- 前端只展示可用能力；后端同样校验开关，不能只依赖隐藏入口。
- 购买关闭不影响既有订单查询、会员记录与必要的售后访问。
- 运营配置加载失败时，允许对已经生成的图片免费保存；不凭空开放购买或异步检测。不在用户看完广告后临时改变本次任务的保存条件。
- 配置接口及业务 API 不经 CDN 缓存；配置可短期本地缓存，但要有版本和有效期。
- 隐私说明准确反映照片上传、临时文件、保留期限、第三方检测、删除方式与运营主体。

验收：新 Fork 不配置自己的域名就无法发布构建；无请求误发上游；免费部署不出现会员购买、异步检测演示或内部诊断入口；协议与实际部署一致。

### 1C. 一次制作任务的失败恢复

- 为当前制作维护统一草稿：照片文件引用、规格、模型、底色、参数、处理状态、已生成结果。
- 区分选择照片、上传、处理、结果、保存等状态；同步接口尚不能提供真实阶段进度时显示等待状态，不伪造百分比。
- 无人脸/多人脸引导重新选图；网络异常可重试；服务繁忙避免连续重复提交；相册失败只重试保存。
- 普通失败不清空原图和参数；编辑已生成结果时失败，保留上一份成功结果。
- 保存草稿用本地文件与少量元数据，不将完整图片长期塞入同步缓存；设定清理期限和用户手动清理入口。
- 明确“最近照片”的保留数量和替换规则，不能无提示覆盖旧照片。
- 暂不默认自动重试长耗时生成请求，因为断线后后端可能仍在处理。

验收：断网、无脸、多脸、返回异常、拒绝相册权限均不会丢失已完成选择；退出重进后的恢复能力与界面承诺一致；清理临时文件不删除相册照片。

## 第 2 阶段：一份镜像的可选完整部署

### 服务组织

| 服务 | 启动方式 | 数据与访问 |
| --- | --- | --- |
| API | 默认启动，单个 Uvicorn worker | 端口可配置，当前 NAS 使用 8090；公开图片/登录接口 |
| push | 可选 Compose profile | 共用身份/订单数据；仅公开微信验签与回调路径 |
| admin | 独立可选 profile | 共用运营数据；默认宿主机回环访问，远程使用 VPN/隧道，或显式配置受限局域网入口 |

### 范围

- 三个服务使用同一镜像、不同启动命令，默认一条命令只启动 API；文档给出按需增加服务的命令。
- 宿主机端口与数据路径通过配置控制，避免每次修改受 Git 管理的 Compose，后续 `git pull` 不与 NAS 端口修改冲突。
- 镜像必须包含管理后台 HTML/CSS/JS 等资源；当前 Dockerfile 只复制 Python 文件，不能直接宣称支持完整后台。
- 后台在容器内监听可访问的地址，但宿主机端口按访问策略限制；不直接沿用只监听容器回环的原始启动方式。
- 每个服务使用符合自身接口的健康/就绪检查，不能复用 API 的 `/health` 来检查 push/admin。
- 每个服务只取得所需环境变量；只有启用推送/支付/后台时，才校验对应配置。
- SQLite 与 identity.key 放本地持久化卷，单机先保留 SQLite。验证多个服务并发读写、密钥初始化和备份恢复。
- 图片推理、推送、管理进程隔离，避免后台或回调等待图片计算。
- 支付仍须显式开启；启用前验证平台资格、签名、幂等、到账、退款与通知重放，不通过容器启动就判断可支付。
- EdgeOne/Lucky 配置记录在独立部署文档中：公网 HTTPS、协议/端口匹配、请求体大小、超时、API 不缓存、回调路径分流。
- 固定经过验证的后端依赖，记录镜像版本，增加镜像导入与启动检查。优先支持 linux/amd64。
- 增加实际图像推理冒烟检查，区别于只证明进程存活的 `/health`；发布验证使用可公开的测试素材，不记录用户原始照片。

### 验收

- 从干净配置可分别启动 API、API+push、完整三服务。
- 不启用可选服务不会因缺少支付/后台密钥而阻止 API 启动。
- 回调通过微信实际验签和事件验证；后台页面及静态资源完整，访问范围符合配置。
- 停止容器后完整备份并恢复一次；恢复后会员身份和订单关联不丢失。
- 与上一阶段同一组图片处理和保存回归继续通过。

## 第 3 阶段：仓库整理与可维护性

- 将零散电子照控制台脚本和过时调试说明归档到 `docs/debug/`；验证有效性后保留或移除，修正文档引用。
- macOS LaunchAgent 恢复脚本明确归档为 macOS 专用，不作为 Windows/fnOS 启动入口；移除可替换的个人默认路径。
- 主项目只承诺微信和 H5，精简未安装对应构建依赖的平台命令；不把精简脚本当成已完成全平台迁移。
- README、环境示例、Docker 文档只保留一致的安装和部署入口；区分已验证能力、可选能力与未验收能力。
- 前端 CI 验证 Node 24 / Yarn 锁文件 / 微信和 H5 构建；后端 CI 验证异常处理、能力开关、回调与镜像启动。
- 不自动提交本地 AppID 改动、环境文件、NAS 数据或其他用户未确认的工作区修改。

验收：新维护者仅依据 README 即可找到正确部署路径；无个人路径和真实上游地址被当作默认生产配置；CI 检查与公开支持范围一致。

## 后续独立迭代

1. 长耗时任务：有界队列、任务编号、幂等提交、状态查询、断线恢复、授权结果下载和过期清理。基于 NAS 实际延迟决定何时启动，不先引入完整分布式架构。
2. 本地工具：评估水印、压缩、格式转换、部分排版在设备端处理，逐项验证真机内存、透明度和输出质量。
3. 前端迁移：单独评估 Vue 3 / 新构建工具对 uView、class decorators、Vuex、相机和微信组件的影响，建立页面/交互基线后逐步迁移。
4. 运营：观察生成耗时分布、成功率、保存率和资源成本，再确定广告和付费方式。记录必要元数据，不采集原始照片作为普通日志。

## 建议交付批次

1. 当前修复基线：提交、同步 NAS、真实照片验收与回退记录。
2. 免费保存策略：统一保存入口和重试授权，先解决当前无法保存。
3. 自有配置与能力：清理上游默认值、构建检查、界面/后端开关一致。
4. 制作失败恢复：保留照片、参数、结果，统一状态和错误提示。
5. 可选完整部署：端口可配置、push/admin、静态资源、镜像验证、备份恢复。
6. 仓库清理与文档收口；达到验收条件后发布第一个可复现版本。

每批独立提交和验证。依赖上游的改动集中维护，不将用户照片、密钥或生产数据库加入测试。
